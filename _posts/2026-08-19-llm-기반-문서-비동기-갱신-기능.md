## **구현 기능 한 줄 정리**

> "문서 1건당 70~125초 걸리는 LLM 호출을 HTTP에서 분리하면서, **스레드풀 크기·트랜잭션 경계·폴링 페이로드를 전부 다운스트림 제약(LLM의 한계 수치)에서 역산**해 설계했다."
> 

## 구현 기능 개요

- **기능 정의:** 사용자가 작성한 문서를 외부 LLM API를 활용해 자동 교정·보완하고 갱신하는 기능
- **핵심 목표:** 1건당 **70~125초**가 소요되는 고비용 I/O 작업을 HTTP 웹 요청과 격리하여, **서버 셧다운을 방지하고 빠른 사용자 응답(UX)을 확보**

---

## `@Async` 도입 배경

### ❌ 기존 동기(Synchronous) 방식의 문제점

1. **HTTP 타임아웃 발생 (504 Gateway Timeout)**
    - Nginx나 브라우저의 기본 타임아웃 한계는 보통 30~60초입니다.
    - 70~125초가 걸리는 LLM 처리를 동기로 기다리면 클라이언트는 100% 타임아웃 에러를 맞이합니다.
2. **Tomcat 서블릿 스레드 고갈 및 서비스 전체 마비**
    - 웹 요청을 처리하는 Tomcat 스레드가 125초 동안 아무것도 못 하고 블로킹(Blocking)됩니다.
    - 무거운 LLM 요청 몇 개만 들어와도 Tomcat 스레드풀이 동나서, **로그인이나 단순 조회 같은 일반 기능까지 전부 먹통**이 됩니다.

### ✅ 비동기(Asynchronous) 방식 도입으로 해결

- **Tomcat 스레드의 즉시 해방 (0.01초 응답)**
    - 요청이 들어오는 즉시 작업을 백그라운드 전용 스레드로 넘기고, 클라이언트에는 **`202 Accepted` 응답과 `Task ID`를 즉시 반환**합니다.
- **작업의 자원 격리**
    - 무거운 LLM 작업이 웹 요청 스레드에 영향을 주지 않도록 **독립된 비동기 스레드풀**에서만 안전하게 실행되도록 분리했습니다.
- **Non-blocking UX 구현**
    - 사용자는 화면이 멈추지 않고, 반환받은 `Task ID`를 통해 상태를 확인(Polling)하며 다른 작업을 계속 진행할 수 있습니다.

## `@Async`의 흐름

**Spring**에서 `@Async`는 **AOP(Aspect Oriented Programming)** 프록시를 통해 동작한다.

```
[HTTP 요청 스레드 (Tomcat)]
   │
   1. docRevisionService.updateDocumentAsync() 호출
   ▼
[Spring AOP Proxy 가로챔]
   │
   2. 작업을 Runnable 객체로 포장
   3. documentRevisionExecutor (ThreadPoolTaskExecutor)에 submit()
   ▼
[ThreadPoolTaskExecutor 큐/스레드풀]
   │
   ├─► (HTTP 스레드): 즉시 작업 ID(Task ID) 반환 후 HTTP 응답 (202 Accepted)
   │
   └─► (doc-revision-x 스레드): 큐에서 작업 꺼내어 백그라운드에서 70~125초 LLM 호출 실행
```

1. 프록시의 개입: 클라이언트 요청을 Tomcat 스레드가 `@Async` 메서드를 부르면, 실제 객체가 아닌 **Spring AOP 프록시 객체**가 요청을 가로챘습니다.
2. **작업 제출:** 프록시는 메서드 실행 로직을 `Runnable` 작업 단위로 감싸 지정된 `documentRevisionExecutor`에 제출(`submit()`)합니다.
3. **HTTP 스레드 즉시 반환:** 작업이 스레드풀 큐에 들어가면, Tomcat 스레드는 70~125초 동안 기다리지 않고 **즉시 202 Accepted 응답을 반환**하여 다음 HTTP 요청을 받으러 돌아갑니다.
4. **비동기 실행:** 백그라운드 전용 스레드(`doc-revision-1`)가 큐에서 작업을 꺼내 외부 LLM API 호출 및 후속 처리를 진행합니다.

## Runnable 객체란?

### **1. 🍽️ 비유로 이해하기 (식당의 셰프와 주문서)**

- **스레드(Thread) = 셰프 (일하는 사람)**
- **Runnable 객체 = 주문서 (무슨 요리를 어떻게 할지 적힌 종이)**

식당에서 셰프(스레드)가 일을 할 때, 셰프 자체가 요리가 될 수는 없습니다. 손님이 들어오면 "**1번 테이블 스테이크 미디움으로 조리하기"**라는 내용이 적힌 **주문서(Runnable)**가 생성되어 큐(주문 꽂이)에 꽂힙니다.

그러면 셰프(스레드)는 큐에서 **주문서(Runnable)**를 하나씩 꺼내어 거기에 적힌 작업(`run()`)을 수행합니다. 요리가 끝나도 셰프(스레드)는 퇴사(종료)하지 않고 다음 주문서(Runnable)를 기다립니다.

### **2. 🤔 왜 굳이 `Runnable`로 일감을 포장할까요?**

**"일하는 주체(스레드)"와 "해야 할 일(작업)"을 분리하기 위해서입니다.**

만약 일감과 스레드가 하나로 묶여 있다면, 일을 할 때마다 억 단위 비용이 드는 스레드를 새로 만들고 지워야 합니다.

하지만 **일감을 `Runnable` 객체로 예쁘게 포장**해 두면:

1. 일감(`Runnable`)만 생성해서 **스레드풀 큐(Queue)**에 차곡차곡 쌓아둘 수 있습니다.
2. 스레드풀에 미리 만들어둔 5개의 스레드가 큐에서 `Runnable`을 하나씩 꺼내어 `run()` 메서드를 대신 호출해 줍니다.
3. 작업이 끝나면 스레드는 죽지 않고 재사용됩니다.

## 스레드풀 활용

- **→ 스레드풀이란?**
작업을 실행할 스레드를 매번 새로 만드는 대신, 미리 만들어둔 스레드 여러 개를 재사용 하는 것
    - **스레드풀의 구성요소**
        - 코어 풀 사이즈: 평소 유지하는 기본 스레드 개수
        - 맥스 풀 사이즈: 최대 스레드 개수
        - 큐
        - 거부 정책: 큐와 스레드가 맥스에 도달했을 때 추가 작업이 들어왔을 때 어떻게 할지

```java
@Bean
ThreadPoolTaskExecutor documentRevisionExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(5);
    executor.setMaxPoolSize(5);
    executor.setThreadNamePrefix("doc-revision-");
    executor.initialize();
    return executor;
}
```

**→ @Bean을 둔 이유**

- **이름으로 `@Async`가 찾을 수 있게**
@`Async(”documentRevisionExecutor”)`가 이름으로 찾는 대상이 바로 이 빈이다
만약 ThreadPoolTaskExecutor를 빈으로 등록하지 않고, @Async에 이름도 넣지 않았다면 Spring은 매치되는 Executor빈을 찾지 못하고 기본값인 SimpleAsyncTaskExecutor로 폴백한다
- **앱 전체에 딱 하나만 존재하게**
`@Configuration` 클래스 안의 @Bean 메서드는 Spring이 앱 시작 시 딱 한 번만 호출해서 그 결과를 컨테이너에 등록하고 이후 누가 이 빈을 필요로 하든 항상 같은 인스턴스를 재사용한다
- **Spring이 시작,종료를 관리해주게**
`ThreadPoolTaskExecuotr`는 Spring의 라이프사이클 인터페이스를 구현하고 있어서, 빈으로 등록되면 Spring이 애플리케이션을 종료할 때 자동으로 이 풀의 shutdown()을 호출해준다.

## **Backpressure(배후압) 역할을 한다는 게 무슨 의미인가?**

### **1. Backpressure란?**

유입되는 요청의 속도(상류/Upstream)가 시스템이 처리할 수 있는 속도(하류/Downstream)보다 빠를 때, **부하를 하류의 처리 능력에 맞추어 제어하거나 거부하는 매커니즘**입니다.

### **2. 왜 LLM 호출에서 Backpressure가 필수인가?**

- LLM API는 1건당 **70~125초**가 걸리는 극단적으로 느린 I/O 작업입니다.
- 외부 LLM Provider는 **RPM/TPM(분당 요청/토큰 수) 제한**을 두고 있습니다.
- 무제한으로 비동기 스레드를 생성하면, 메모리가 고갈(OOM)되거나 외부 API 레이트 리밋에 걸려 전체 비동기 작업이 떼거지로 실패합니다.

### **3. 스레드풀과 큐를 통한 Backpressure 구현**

스레드풀의 `CorePoolSize(5)`, `MaxPoolSize(5)`, `QueueCapacity` 및 거부 정책(RejectedExecutionHandler)을 설정함으로써 **시스템이 견딜 수 있는 한계선**을 그을 수 있습니다.

- **정상 상태:** 5개 이하의 작업은 5개 전용 스레드가 1:1로 즉시 처리합니다.
- **지연/지옥 상태:** 처리 속도보다 요청이 더 빨리 들어오면 큐에 대기합니다.
- **임계치 초과 (Backpressure 발동):** 큐까지 가득 차면 추가 요청을 받지 않고 `TaskRejectedException`을 발생시킵니다.
- **결과:** 애플리케이션 서버가 뻗는 대신, HTTP 레이어에서 **429 Too Many Requests** 또는 **503 Service Unavailable** 응답을 상류(클라이언트)에 즉시 전달하여 시스템 전체 폭사를 방지합니다.

## **세마포어 (Semaphore)**

### 세마포어란?

앞서 설명하던 스레드풀이란 내 서버 안의 스레드 제한을 위한 기술인데 반해, 세마포어를 통해 얻고자하는 이득은 외부 타겟 자원(현재는 AI 호출)에 대한 동시 접근 제한을 위한 기술이다

#### 활용 장점

1. **스레드는 수십 개를 띄우되, 외부 LLM 호출만 n개로 조이고 싶을 때(자원 격리)**
→ 내 서버의 스레드 개수와 외부 API의 제한 수치를 서로 독립적으로 분리해서 관리할 수 있다
2. **다양한 외부 API별로 동시성을 따로 제한하고 싶을 때**
→ 만약 우리의 서비스가 GPT와 Cluade를 동시에 부르고 싶다면 스레드풀을 서비스별로 쪼개서 수십 개로 만들 필요 없이, 하나의 대형 스레드풀을 공유하면서 외부 타겟별로 동시성 세밀 제어 가능
3. **Java21 + 가상 스레드 시대의 표준 패턴**
→ 가상 스레드를 활용할 때는 스레드풀 자체를 아예 만들지 않는다. 대신 수만 개의 가상 스레드를 띄우고, 외부 자원을 호출할 때만 Semaphore를 사용해 동시성을 제한하는 것이 자바 현대 아키텍처의 표준 패턴이다

### **💡 깔끔한 요약**

| **구 분** | **스레드풀 (ThreadPool)** | **세마포어 (Semaphore)** |
| --- | --- | --- |
| **제한 대상** | **내 서버의 일꾼(Thread) 개수** | **외부 자원/API로 나가는 출입표(Permit) 개수** |
| **목적** | 내 서버의 CPU/메모리 고갈 방지 | 외부 API의 Rate Limit 방지 및 타겟별 동시성 격리 |

즉, **"스레드풀은 내 서버의 일꾼 수 통제", "세마포어는 외부 API 문지기"**라고 생각하면 된다

### **스레드풀이 있는데 왜 세마포어를 고려하는가?**

스레드풀은 **"작업을 수행할 실행 자원(Thread) 자체를 제한"**하는 방식입니다. 하지만 외부 LLM API 호출 같은 작업은 스레드가 CPU를 쓰는 것이 아니라 **대부분 I/O 대기 시간(Waiting)**이다.

경우에 따라 **스레드는 비동기 I/O나 가상 스레드(Virtual Thread)로 수백 개를 띄우되, 외부 LLM API로 동시 나가는 요청 수만 엄격하게 제한**하고 싶을 때 `java.util.concurrent.Semaphore`를 결합한다.

```java
publicclassLlmRateLimiter{
// 동시 LLM 호출을 최대 5개로 제한하는 허가증(Permit) 발행기
privatefinalSemaphore semaphore=newSemaphore(5);
publicStringcallLlmWithLimit(String prompt){
try{
// 허가증 획득 (5개가 모두 사용 중이면 여기서 대기)
            semaphore.acquire();
return llmClient.generate(prompt);// 70~125초 소요
}catch(InterruptedException e){
Thread.currentThread().interrupt();
thrownewBusinessException(ErrorCode.LLM_INTERRUPTED);
}finally{
// 작업 완료 후 허가증 반납 (다음 대기 작업 진입 가능)
            semaphore.release();
}
}
}
```

- **동시성 제어(Concurrency Control):** 스레드 개수와 상관없이 **"동시에 외부 LLM API를 타고 있는 요청 수"**를 정확히 5개로 고정합니다.
- **자원 격리:** 특정 동시성 한도를 넘어서면 세마포어 획득 과정에서 대기하거나 즉시 튕겨냄으로써 다운스트림(LLM 서버/DB)의 인프라를 보호합니다.

## **트랜잭션 경계 역산 설계 (가장 중요한 포인트)**

LLM 호출 시 가장 흔히 하는 실수가 **`@Transactional` 안에서 70~125초 동안 LLM을 호출하는 것**입니다.

### **❌ 잘못된 설계 (DB 커넥션 고갈)**

```java
@Transactional// 70~125초 동안 DB Connection을 잡고 있음!
@Async("documentRevisionExecutor")
publicvoidupdateDocumentAsync(Long docId){
Document doc= documentRepository.findById(docId)...;
String result= llmClient.call(...);// 125초 대기 💣 (HikariCP 커넥션 풀 고갈)
    doc.update(result);
}
```

- HikariCP 커넥션 풀 기본 크기는 보통 10개입니다.
- 10명의 사용자가 LLM 생성을 요청하면 **DB 커넥션 10개가 125초 동안 마비**되어, 단순 조회 요청을 하려는 다른 일반 사용자들까지 DB 커넥션을 얻지 못하고 500 에러를 맞게 됩니다.

### **✅ 개선된 트랜잭션 경계 분리 설계**

```

[비동기 스레드 시작]
   │
   ├─ 1. DB 조회 (짧은 트랜잭션) ──► Connection 즉시 반납
   │
   ├─ 2. LLM API 호출 (70~125초) ──► DB Connection 전혀 안 잡음!
   │
   └─ 3. DB 결과 저장 (짧은 트랜잭션) ──► Connection 즉시 반납
[비동기 스레드 종료]
```

```java
@Service
@RequiredArgsConstructor
publicclassDocumentRevisionFacade{
privatefinalDocumentReader documentReader;
privatefinalLlmClient llmClient;
privatefinalDocumentWriter documentWriter;
@Async("documentRevisionExecutor")
publicvoidupdateDocumentAsync(Long docId){
// 1. 트랜잭션 1: 프롬프트 생성용 데이터만 조회 후 커넥션 바로 반납
String prompt= documentReader.readPromptData(docId);
// 2. 트랜잭션 밖: 70~125초간 LLM 호출 (DB Connection 소유 X)
String revisedContent= llmClient.generate(prompt);
// 3. 트랜잭션 2: 결과를 DB에 저장할 때만 순간적으로 커넥션 잡고 반영
        documentWriter.saveRevisionResult(docId, revisedContent);
}
}
```

#### 그래서 트랜잭션 역산 설계를 어떻게 해야하는데?

- **"역산(Bottom-up) 설계"**라는 것은 개발자가 코드를 짤 때 **"다운스트림(외부 LLM)의 125초라는 물리적 한계"부터 거꾸로 계산해서 트랜잭션의 시작과 끝(경계)을 최소한으로 줄여서 설계했다**는 의미이다.

#### **일반적인 방식 (생각 없이 짜는 방식):**

> "메서드 시작할 때 `@Transactional` 걸고, DB 읽고, LLM 부르고, DB 저장하고 메서드 끝내야지~" (결과: 125초 동안 커넥션 점유 💣)
